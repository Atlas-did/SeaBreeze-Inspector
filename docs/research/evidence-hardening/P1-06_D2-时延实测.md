> 对应计划:`SeaBreeze_攻坚计划_v1.md` P1-6 · 证据脚本 `research/专项/D2/latency_profiler.py`

## 1. 结论先行

| 项 | 现状 | 改造后 |
|---|---|---|
| 数据来源 | `measure_once()` 里全部是 `np.random.default_rng().normal(...)` 模拟值 | 真机插桩:采集/预处理/推理/决策/执行五段实测 |
| 可引用性 | **不可引用**(脚本自己都打印「模拟量,实机需真插桩」) | 报告标注「实测」+ 测量协议,可进论文 |
| 口径 | 只报 P50 | 逐段 P50/P95/P99 + 满载/空闲对比 |
| 成本 | —— | 你出硬件(Tello + Arduino + SG90),我写插桩脚本;1-2 天 |

**为什么必须做**:系统闭环时延 ≤100ms 是评审硬指标(攻坚方案 §五,5 分)。当前控制周期 dt=0.1s(100ms)本身就踩线,加上视频采集→推理→决策→串口→PWM→伺服,真实总时延大概率 120–200ms。这个数字**必须实测出来、如实报**,因为:(a) 审稿人问「闭环总时延多少」你答不出来或答个模拟值,直接减分;(b) 如果真实时延 >100ms,控制方案里 EKF 预测 + 前馈的设计恰好是为了在长时延下保持性能——**长时延反而是你论文讨论的一个真实、有深度的点**,前提是你知道它到底多长。

## 2. 问题定位

`D2/latency_profiler.py` 的核心是 `measure_once()`:

```python
sensor = np.random.default_rng().normal(15e6, 3e6)   # ~15ms 模拟采集
pre    = int(np.random.default_rng().normal(2e6, 0.5e6))
percep = int(np.random.default_rng().normal(30e6, 5e6))
decis  = int(np.random.default_rng().normal(1e6, 0.2e6))
act    = int(np.random.default_rng().normal(25e6, 5e6))
```

五个段全部是固定均值的高斯采样。报告 `latency_report.json`(total P50=73.4 / P95=85.7 / P99=90.3)就是这些模拟值的统计,**与真机零关系**。脚本头部注释与输出提示也明说了「模拟量,实机需真插桩」。

代码框架本身是有价值的——`t0→t1→t2→t3→t4→t5` 分段 + monotonic 时钟 + 分位点统计的骨架可以保留,只要把每段的取值从 `np.random` 换成真机测量即可。**改造是「填肉」不是「推倒」。**

## 3. 改造方案

### 3.1 链路与时戳定义(先定口径,别自说自话)

```
t0  采集开始(摄像头曝光)     →  Tello 视频帧到达主机的时刻(见 3.2)
t1  预处理完成(缩放/归一化)   →  预处理函数返回时刻
t2  感知推理完成(输出检测框)   →  detect() 返回时刻
t3  决策发出(FSM 决定机械臂动作) →  MessageBus 发布时刻
t4  执行指令到达 Arduino       →  串口写完成时刻(主机侧)
t5  伺服开始动作               →  串口读回 ACK / 外接计时
```

**同机分段用 `time.perf_counter_ns()`(monotonic,不受系统时间跳变影响)**;跨机段(Tello 视频流 → 主机)用协议级时间戳,见下。

### 3.2 各段怎么测(Tello 链路,重点)

- **视频采集段(t0→t1 中属「获取帧」的部分)**:Tello 通过 RTSP 推视频流。在 `vision` 模块里,`VideoCapture.read()` 返回的是解码完成时刻,拿不到曝光时刻。可行办法:① 用 Tello 的 `command` SDK 对 `takeoff/land` 等有明确响应时间的命令测「指令→响应」往返;② 视频帧间到达时间戳统计帧率与抖动(作为采集段的间接证据);③ 若要曝光时刻,可用 Tello 遥测里的帧序号 + 主机接收时间戳做管道延迟估计。**论文口径**:报告「主机侧逐帧到达间隔 P50/P95 + 曝光不确定性注明」。
- **预处理段(t1−t0)**:主进程里 `cv2.resize`/归一化前后各打一次 `perf_counter_ns`。
- **推理段(t2−t1)**:`model.predict(...)` 调用前后打点。**注意用 `torch.inference_mode()` + CPU/GPU 固定 batch=1**,并且要区分「单帧纯推理」与「管线含预热」。论文还要顺手报**推理帧率 FPS**(评审硬指标 ≥20fps 的答案也在这)。
- **决策段(t3−t2)**:FSM 状态转移 + MessageBus 发布,毫秒级,测它为了完整。
- **执行段(t5−t4)**:Arduino 串口回环测通信;SG90 转到位的时间用 C1 台架 + 手机录像逐帧量(或 Arduino 用模拟量反馈估)。真实伺服转动 60° 一般 0.1–0.3s,这一段**大概率是总时延大头**,务必实测。

### 3.3 测量协议(让数字可复现、可辩护)

1. **预热**:正式采样前跑 50 帧预热(CPU 调度、模型 warmup、串口缓冲都稳定后再计时);
2. **采样量**:每段 ≥500 次(N=1000 更稳),按 `--n` 参数控制;
3. **负载条件**:分别测「空闲」(仅管线跑)与「满载」(控制器 + 视觉 + 通信全速)两种,论文报两行;
4. **稳态**:连续采样,丢弃前 10% 作预热区;统计 P50/P95/P99;
5. **时钟**:全机同一 `perf_counter_ns` 基准;跨机段注明方法。

### 3.4 脚本改造清单(我提供,你跑)

- `measure_once(percep_fn, pre_fn, act_fn)` 改成**接收真机回调**,不再内置 np.random;
- 新增 `instrumented_pipeline.py`(或改造 `latency_profiler.py`),把 `backend/` 的视觉/决策/执行模块接进来打点;
- 报告新增字段:`mode: 'real'|'simulated'`、`n_trials`、`warmup`、`load:'idle'|'full'`、每段标注测量方法;
- 输出一张分段堆积条形图(P50)供论文使用。
